# Bespoke holiday enquiries

The existing three-stage `/plan-my-holiday` form is connected to private storage and the working Supabase/Resend enquiry services. Its questions, review stage and styling are retained. There is no automatic connection to New Travel booking systems or suppliers.

1. In Supabase SQL Editor, run **`supabase/migrations/20261027_bespoke_enquiries.sql`** after the existing Articles/offer-enquiry setup. This single, re-runnable migration adds `bespoke_enquiries`, its indexes, Jay-only read policy and a service-only receive function. It does not alter existing data or tables.
2. Set **`BESPOKE_ENQUIRIES_ENABLED=true`** in the existing Vercel environment for the intended deployment, then deploy normally. Reuse the current Supabase and Resend settings. There are no new credentials, mail providers or delivery-approval flags. Until this setting is present, both the public form and endpoint remain closed. Set it to false and redeploy to close the bespoke route independently of offers.
3. Submit one controlled brief at `/plan-my-holiday` with Jay's own contact details. Check its reference and acknowledgement, **Admin > Bespoke Enquiries > View Details**, and the actual inbox/junk folder. Check every answer, children's ages, total party budget and Reply-To. An accepted Resend receipt is not itself proof of mailbox arrival.

## Six-digit reference correction: application order

1. **Deploy the updated application first.** It accepts the original references during the transition and six-digit references afterwards. Do not run the correction while the old PBJ-only server is deployed. Already-open old form tabs get a refresh instruction before any data is saved; the questions and answers are not changed by this format check.
2. In Supabase SQL Editor, run **`supabase/migrations/20261027_bespoke_enquiry_references.sql`** once. Do not edit or rerun `20261027_bespoke_enquiries.sql`. No new environment settings are needed.
3. Refresh `/plan-my-holiday` and submit one controlled owner enquiry. Its confirmation, Admin entry and email should show the same six-digit string, including any leading zeros. This correction has not been applied to hosted Supabase or deployed by the assistant.

New references are cryptographically generated by PostgreSQL and stored as text from `000000` to `999999`, unique within bespoke enquiries. Each save tries at most 64 candidates using the existing unique index to handle collisions, including concurrent ones. Each candidate uses bounded rejection sampling from the random bits of `gen_random_uuid()` to avoid modulo bias. Exhaustion fails safely without acknowledging a saved enquiry. There is no sequence or reference-management interface, and Holiday Offer references are unchanged. PostgreSQL documents [random v4 UUID generation](https://www.postgresql.org/docs/current/functions-uuid.html); its [implementation uses strong randomness](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/utils/adt/uuid.c).

### Previously issued references

The migration conservatively treats **every existing PBJ reference as potentially issued**, including pending notifications. It retains that code in the unique, immutable `issued_reference` column and allocates a six-digit canonical `reference` on the same record. Admin shows the numeric reference and **Original customer reference (still valid)**. This is a read-only reconciliation label, not a new management workflow.

The original customer code continues to identify the same enquiry. Repeated confirmations for an existing request and all retries of its original notification keep that code. The email body, subject, submission time and idempotency key stay unchanged, including when Resend accepted an email but its database receipt is missing. Already recorded receipts are not reset or resent. No customer is silently reissued a different reference or automatically sent a change-of-reference email. Original briefs, record/request IDs, timestamps and notification history are retained; table permissions and RLS are unchanged.

The SQL is transactional and re-runnable: subsequent runs retain the numeric mapping and aliases. An unexpected existing format, inconsistent alias or allocation failure rolls the whole correction back. Both reference columns become immutable after the one-time reconciliation. After correction, do not roll the application back to a PBJ-only version; retain this compatible reference handling.

## Daily use and recovery

**Admin > Bespoke Enquiries** lists original submissions, their references and notification status. Open **View Details** to read the whole brief. Pending means sending failed or the delivery receipt is unconfirmed. Retry the saved notification there; do not create another enquiry. For a pending record older than 23 hours, check Resend and the mailbox before confirming a resend. This reuses the offer enquiry recovery rule because Resend idempotency keys last 24 hours.

If an older notification was already accepted, record its verified existing receipt as database owner instead of sending it again:

```sql
update public.bespoke_enquiries
set notification_id='<verified existing Resend email ID>',
    notified_at=now(), last_notification_error=null
where id='<saved internal enquiry UUID>'::uuid and notification_id is null;
```

References use random six-digit strings after the correction; earlier customer references remain valid aliases as described above. The namespace is separate from the unchanged Holiday Offer references. A retry uses the same request UUID; an identical brief from the same coded client within ten minutes also reuses the saved record after a reload. New distinct submissions are limited to three per ten minutes per coded client. Raw network addresses are not stored in enquiry rows. No enquiry answers are saved in browser storage.

The database keeps the original answers and a server-created snapshot of question labels and option descriptions. Later website edits do not rewrite old briefs or retry emails. The mail service can update receipt/error fields, not the saved answers or reference. A successful save with pending mail is acknowledged honestly; a failed save is not acknowledged as received.

Both routes use `/privacy`, the fixed `jay@plannedbyjay.com` recipient and existing administrator permissions. The accessibility option requests a private discussion; no new medical, passport, payment or marketing fields were added. Keep following the existing monthly retention review, normally deleting inactive unsuccessful enquiries 12 calendar months after last meaningful customer contact, including appropriate mailbox/provider copies. The admin inbox does not add a deletion workflow.
