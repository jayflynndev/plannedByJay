# Holiday Offers

## Manual setup

Run **`supabase/migrations/20261026_holiday_offers_cms.sql`** manually in Supabase SQL Editor, as database owner, after the existing Articles, Holiday Types and Suppliers migrations. Do not re-run the original Articles setup. The new migration creates Holiday Offers, offer-to-Holiday-Type links and private offer-enquiry storage/functions. It can be re-run without replacing records. It imports no offers or suppliers and does not alter existing Articles, supplier or Holiday Type records.

For an existing Offers installation, run only **`supabase/migrations/20261026_holiday_offer_references.sql`** next, manually as database owner. For a fresh installation, run it immediately after the Offers setup above. This reference migration converts the old UUID-derived label and backfills all existing offers without changing IDs, URLs, publication dates, versions, content, suppliers, photographs, prices or historical enquiry snapshots. Do not recreate any offers.

For the random-reference correction, manually run **`supabase/migrations/20261027_random_offer_references.sql`** after the existing reference migration and **before deploying the snagging application changes**. Do not rerun the older migration afterwards. References remain six-character text, including leading zeros. New offers use database cryptographic randomness with bounded collision retries and the existing unique constraint. A private reservation ledger prevents reuse after deletion; all previously consumed sequence numbers and numeric enquiry snapshot references are reserved. Never reset the old sequence or delete ledger entries. References remain stable on edits and duplicates receive their own code. Allocation failure leaves no partially saved offer. Jay never enters a number manually; it is an offer reference, not a supplier booking or bespoke enquiry reference.

The correction changes the existing displayed `000001` once, preserving it as an immutable earlier customer reference in the existing editor/list; either reference finds that offer in Admin search. IDs, URLs, prices, versions, dates and enquiry/notification snapshots remain unchanged. Existing issued enquiry references stay valid. If a very old enquiry snapshot has no numeric reference and relies on the offer's current reference for notification retries, the migration reports a NOTICE and retains `000001` to protect that history. Future offers still use random codes. This exception needs no new customer/admin workflow. See [V1-SNAGGING.md](V1-SNAGGING.md) for rollout and checks.

The existing Supabase URL, publishable key, SITE_URL, administrator login and `article-images` library are reused. No new dependencies or environment variables are needed to publish offers. Existing server-only mail/database keys are reused for the prepared enquiry delivery path; their names are documented in .env.example. Nothing has been applied to hosted Supabase, committed, pushed or deployed automatically.

## Enter one offer

Open **Admin → Holiday Offers → Add Offer**. The editor has five sections:

1. **Holiday:** choose an existing active Approved supplier; enter title, destination, accommodation, short description and optional “Why Jay picked it”/formatted highlights. Supplier identity, address, contacts and booking conditions are reused. Follow Edit supplier details if those essential public details are incomplete.
2. **Travel details:** choose the arrangement and, where applicable, flights/departure point. Enter departure plus return date or nights; nights calculate automatically from dates. Add board/fare, room/cabin, priced adults/children, ages where pricing depends on them, inclusions and relevant exclusions.
3. **Price:** enter the total for the stated party, currency and price-check date. Confirm price checked today uses the current UK date; it does not fetch a live price. A per-adult average is optional and displays only for an all-adult party where the amount divides exactly. An optional booking/promotion deadline is inclusive through that UK date. There is no universal seven-day expiry.
4. **Presentation:** choose/upload photographs using the existing library, optionally add up to eight more, select published Holiday Types and one optional sash. Featured on Homepage is an explicit choice, off by default. Leaving Soon only displays within 30 calendar days of departure. Adults Only needs confirmed arrangements and no children in the priced party.
5. **Publishing:** Save Draft, private Preview, Publish or Save Changes. Unpublish asks for confirmation. Drafts can remain incomplete. Results remain beside the buttons and are announced accessibly; failed requests retain the editor. Save regularly; there is no background autosave.

The permanent six-digit reference appears after the first save in the editor and offer list, and on public cards and detail pages. An unsaved preview has no reference; previewing a saved offer reuses its existing reference. Published URLs stay fixed even after unpublishing/archiving. The list supports title/reference search, Edit, Duplicate offer, Unpublish and Archive/Restore with confirmation. A duplicate is a new draft with a distinct URL, homepage featuring off and the price-check date cleared. Existing photographs and Holiday Type links are reused. Archive retains the offer ID and any enquiries; permanent deletion is not exposed. Restore returns an offer to drafts.

## Public display and pricing

One eligible published record supplies `/holiday-offers`, its own `/holiday-offers/[slug]`, selected Holiday Type pages and, only when selected, the homepage featured section. The main catalogue also includes offers with no Holiday Type association. The article section stays in place. Empty related/featured offer sections are hidden.

The catalogue has destination, Holiday Type and departure-month filters plus date/price sorting. Price sorting groups by currency; no exchange-rate conversion is implied. The shared compact card shows the photograph and one sash, title/accommodation, destination, travel date/nights/departure point/board basis, supplier display name, reference, priced party and prominent total, with a View Holiday action. Desktop uses photograph/details/price columns; tablet and mobile reflow naturally. Cards retain the price-check date, concise availability wording, booking deadline when present and full mandatory-charge text beside the price. They omit the supplier's legal name/registration number, address, contacts, booking terms, protection details and long disclaimer; these remain on the individual holiday page. Why Jay picked it uses a short excerpt on cards; the full saved wording remains unchanged on the detail page. A Free Child Place highlight is used only for an explicitly saved, standalone inclusion for a party with children, with no qualifying/negative wording in the inclusions. No benefit is inferred from the supplier or price. Generated metadata, canonical/social images, a WebPage structured-data record and the sitemap use current eligible content. No stock availability or live-price structured-data claim is invented. Existing site-wide noindex remains unchanged.

The individual page leads with the title/accommodation/destination, existing photographs and a responsive travel/party-price summary. Single photographs have no placeholder tiles; additional saved images form a compact supporting gallery. Photographs enlarge in a keyboard-accessible dialog with previous/next controls, Escape/Close and focus returned to the original image. The saved description, inclusions, optional editorial selection and conditions follow in that order. Simple comma-separated or line-separated inclusions become checklist items; ambiguous prose/qualifications stay as paragraphs. The full saved text is retained and no fields need entering again. Supplier business details, terms and applicable protection appear once in an expandable section, with mandatory charges still visible beside the price and the full availability disclosure below. The price action opens the existing final offer-specific enquiry form; its launch controls are unchanged.

Drafts, archived offers, departed offers and expired promotions are absent from public reads and return 404 at their individual URLs. Archiving/downgrading the supplier, or removing its essential identity/contact/terms details, also hides its offers. These checks apply in SQL as well as the application. Public access to the supplier table itself remains disabled: the offers RPC returns only the public fields of suppliers attached to eligible offers. ATOL details are returned/displayed only when the particular offer explicitly claims the confirmed applicable supplier arrangements; they are never copied automatically to every product.

Include known mandatory charges in the party total. For any charge that cannot reasonably be calculated, explain the calculation and when it is payable in Mandatory charges / local taxes; that text appears prominently beside the price. The [ASA travel-pricing guidance](https://www.asa.org.uk/advice-online/travel-marketing-pricing.html) explains the distinction. A changeable supplier price still needs an accurate checking date and review; a disclaimer is not a substitute for entering the correct amount. No prices, supplier credentials or protection claims are seeded.

## Offer-specific enquiries: operational

The existing four-field form now displays a read-only summary of the saved holiday. The server validates contact data, stores an authoritative holiday snapshot through the existing RPC and uses the existing Resend configuration for a fixed-recipient notification with Reply-To and submission date/time. No private key or customer-supplied price is trusted in the browser.

**Offer enquiries are operational.** Jay has confirmed public submission, private storage, actual inbox arrival and the correct on-screen acknowledgement. The Privacy Policy is published and `deliveryVerified` remains true. No offer activation change or migration is required for bespoke setup.

If the database accepts an enquiry but email/receipt recording fails, the customer gets an honest saved-but-notification-pending acknowledgement. The private record remains available at `/admin/offer-enquiries` for a controlled notification retry. Pending records, stored receipts and original snapshots survive failures; unchanged idempotency keys/payloads prevent duplicate acceptance in Resend's retry window. Older pending messages require a mailbox/Resend check before resending. Accepted by Resend never claims actual mailbox arrival.

See [OFFER-ENQUIRY-LAUNCH.md](OFFER-ENQUIRY-LAUNCH.md) for the confirmed live status and recovery procedure. No new offer gate, service, background scheduler or customer-management system is introduced. The bespoke Holiday Brief now shares the existing services, with one separate migration and activation setting; see [BESPOKE-ENQUIRIES.md](BESPOKE-ENQUIRIES.md).

## Validation limits

Automated tests use an isolated PostgreSQL fixture and synthetic offers/supplier details. They do not prove that a real Jet2holidays supplier is present or that hosted sign-in, upload, publication or email delivery works. The owner must run the migration and verify those live behaviours after a separately authorised release. The application never creates test offers in the hosted project.

Local regression checks cover reference backfill/preservation, leading zeros, duplicate saves, deletion/rollback, immutable references, uniqueness/exhaustion and saved-reference enquiry notifications. Public layout checks use a read-only copy of the published Sol Tenerife offer with the updated components and production CSS. These checks do not apply the hosted reference migration, enable enquiries or prove live mail delivery.
